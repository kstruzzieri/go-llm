### Fixed — A file deleted while the sandbox checks the workspace no longer refuses the command (#845)

Before each sandboxed command (Bubblewrap on Linux, Seatbelt on macOS), Golem checks the whole workspace for files hard-linked to a name outside it and for the git metadata the sandbox protects. A file or directory that another process deleted during that check, such as the loose objects git's automatic `gc` removes after a commit, an editor's temporary file or a build tool's output, refused the command with `tools: sandbox inspect workspace entry "...": ... no such file or directory`. Now a check that sees the workspace change under it (an entry it listed is gone, or a file's link count changes) starts again from the beginning, up to three checks in all, and the command runs on the first check that saw no change. That check is the same as before, so a file linked outside the workspace is still refused, and the `.git` of a directory renamed during the check is still found under its new name. If the workspace changes during all three checks, the command is refused with `tools: sandbox workspace changed while inspecting "<path>": ...; retry`. Any other error, and a workspace root that is gone, still refuse the command at once. While the workspace keeps changing, the check before a command can take up to three times as long.
