# Upgrading to go-llm v0.9.0

Read this before upgrading from v0.8.0. For older dependencies, apply the
[v0.8.0 upgrade guide](v0.8.0.md) first; it links the earlier notes in turn.
The v0.9.0 section of the [changelog](../../CHANGELOG.md) contains the full
entries.

v0.9.0 lets a Go, git or Python toolchain outside the workspace run under the
macOS Seatbelt sandbox, and hardens the git commands Golem itself runs on the
host against a bare repository a sandboxed command planted in the workspace.

The toolchain roots are opt-in: a session that declares none behaves as in
v0.8.0, and its approval key is unchanged. The git hardening is on in every
Golem session that runs git. Check five things: parallel task mode now needs
git 2.38 or later, Golem refuses a `git` that lies inside the workspace, a
repository whose local config includes other files loses its git context
block, hooks and filters run by Golem's git no longer find programs in
workspace directories, and parallel task mode no longer runs `core.fsmonitor`
helpers. Library hosts should also check their
`errors.Is(err, tools.ErrSandboxPolicy)` handling
([below](#library-additions-and-api-changes)).

A bare repository planted in the workspace is still a risk to git that you or
your editor run there. Set `safe.bareRepository=explicit` in your own git
configuration; [Known issues](#known-issues) says how. Bubblewrap still cannot
refuse git metadata created during a run; that fix (#802) moved to v0.10.0.

## Changed defaults and new requirements

### Golem's own git calls refuse a planted bare repository (#803)

A sandboxed command can create a directory git treats as a bare repository.
Golem runs git on the host for the session's git context snapshot (at startup
and on `/git-context refresh`) and for parallel task mode (`-plan-workers`
above 1). Every one of those git commands now passes
`-c safe.bareRepository=explicit -c core.fsmonitor=false`, so a bare repository
found by discovery in a workspace with no `.git` of its own is refused, and no
`core.fsmonitor` helper runs. The snapshot runs in host and native sandbox
sessions alike; parallel task mode runs only in host sessions, since the
AgentFlow modes reject `-sandbox`.

- **Parallel task mode needs git 2.38 or later.** Golem runs `git --version`
  once for each git binary and refuses an older one with
  `Golem needs git 2.38 or later`. The snapshot already needed 2.45 for
  `--no-lazy-fetch`. This refusal, and the next one, also disable the snapshot,
  which at startup shows as `git context disabled: ...`.
- **A `git` inside the workspace is refused.** Golem refuses a `git` found on
  `PATH` that, once symbolic links are resolved, lies inside the workspace, and
  a relative `git` path. With `-root` set to your home directory, this refuses
  `~/bin/git` and asdf or mise shims installed under it. This is intended: a
  sandboxed command can write anywhere in the workspace.
- **Config includes disable the snapshot.** A repository whose local or
  worktree config includes another file (`include.path` or
  `includeIf.<condition>.path`) starts with `git context disabled: ...` instead
  of the git context block. `/git-context refresh` prints
  `git context refresh failed: ...` and keeps the previous block. Parallel task
  mode does not apply this check.
- **`PATH` is filtered for every git Golem runs.** Golem drops empty, relative
  and nonexistent `PATH` entries, entries inside the workspace, and entries it
  cannot resolve, and passes each remaining directory by its resolved path. If
  no entry is left, Golem refuses to run git. A
  hook or filter that relied on a program in a workspace directory (for
  example through direnv's `PATH_add bin`) no longer finds it. Install such
  tools outside the workspace or call them by an absolute path.
- **Parallel task mode no longer runs `core.fsmonitor` helpers.** On macOS and
  Windows, where git has a built-in monitor, `status` in parallel task mode may
  be slower.

Parallel task mode still runs the repository's own hooks, filters (git-lfs
keeps working) and lazy fetch, with the environment Golem builds. Details:
[Golem's own git calls](../golem.md#golems-own-git-calls).

### Library additions and API changes

Additive. An unkeyed literal of a struct that gained a field stops compiling:
`agent/tools`' `SandboxConfig` and `golem.CommandPermissions`. Both were
already not comparable, so `==` code is unaffected.

- `agent/tools` (#722): `SandboxConfig.ReadOnlyRoots`,
  `SandboxConfig.DeveloperDirectory`, `SandboxConfig.Env` (a `[]SandboxEnv`)
  and `SandboxConfig.TempEnv`; the `SandboxEnv` type;
  `SandboxConfig.Clone` and `SandboxConfig.EffectiveEnv`;
  `CanonicalToolchainRoot`; and `ActiveDeveloperDirectory`, which on every
  platform but macOS returns an error wrapping `ErrSandboxPolicy`.
- `golem` (#722): `CommandPermissions.ReadOnlyRoots`,
  `CommandPermissions.DeveloperDirectory` and `CommandPermissions.Env`, for
  display.
- **Changed error:** `NewSandboxedExecTools`,
  `NewSandboxedExecToolsWithOptions` and `NewSandboxedBackgroundManager` now
  wrap `ErrSandboxPolicy` when the sandbox backend cannot be built, and the
  exec tool constructors (`NewExecToolsWithBackground` and
  `NewExecToolsWithBackgroundOptions` included) wrap it when a declared root
  overlaps the workspace. `errors.Is(err, tools.ErrSandboxPolicy)` now matches
  backend construction failures it did not match in v0.8.0.
- The Bubblewrap and host runtimes refuse all four new `SandboxConfig` fields
  with `ErrSandboxPolicy`.

The approval key's sandbox component writes the new fields only when they are
set, so a config that declares none keeps the key it had in v0.8.0. Copy a
`SandboxConfig` with `Clone` before keeping or changing it: `Clone` copies
every slice. [docs/library.md](../library.md#native-sandbox-and-declared-toolchain-roots)
describes each field and helper.

## Protections that are opt-in

| Protection | How to turn it on | What it does | What it does not do |
| --- | --- | --- | --- |
| Declared read-only toolchain roots (#722) | `golem -sandbox seatbelt` with `-sandbox-read-root DIR` (repeatable), `-sandbox-env NAME=VALUE`, `-sandbox-temp-env NAME` and `-sandbox-developer-dir`; library hosts set the new `SandboxConfig` fields | Seatbelt commands may read and run the declared folders, never write them. `-sandbox-env` sets variables from a closed table (`GOMODCACHE` inside a declared root, `GOPROXY=off`, `GOTOOLCHAIN=local`, `GOFLAGS=-buildvcs=false`); `-sandbox-temp-env GOCACHE` gives each command a private, cold build cache. `-sandbox-developer-dir` declares the standalone Command Line Tools so `git` and `python3` run. Each root is admitted at startup, shown in the `permissions:` line and in every command and verification approval preview, and part of the approval key. | Bubblewrap and the host runtime refuse all four flags on any OS, so Linux gets none of this yet. A declared root is a path, not a guarded copy: a process outside Golem can change what a command later runs from it. The admission list refuses specific folders (home, `/private/tmp`, broad system folders, credential folders, go-llm's own stores and temp directories), which does not prove an admitted folder holds nothing sensitive. A full Xcode selection, `go.work` workspaces with modules outside the workspace, and cgo are not supported. |

Declared roots give commands no new write access, and the network stays as
`-sandbox-network` says. A root that overlaps the workspace is refused at
startup, when the command tools are built, and again before each command. With
`-sandbox-network allowed`, a command can connect to a Unix-domain socket
inside a declared root, so do not declare a folder that holds sockets a
command should not reach.

`GOCACHE` under each command's private temp is cold for every command: a cold
build of a project the size of go-llm writes several hundred MB to
`/private/tmp`, once per command. A full test suite can need a `run_command`
`timeout_seconds` above the 60-second default (at most 600). The Go recipe,
including how to seed the module cache, is in
[Declared toolchain roots under Seatbelt](../golem.md#declared-toolchain-roots-under-seatbelt).

The rest of the [v0.8.0 table](v0.8.0.md#protections-that-are-opt-in) and the
[v0.6.0 table](v0.6.0.md#protections-that-are-opt-in) still describe what a
default session does not get: strict approval, network narrowing under strict
approval, the native command sandbox, exact configured-secret protection, the
`-interceptors` detectors and MCP HTTP authentication all stay opt-in. Strict
approval asks a person again once outside content is in the conversation; it
does not detect or remove injected instructions
([decision record](../security/strict-mode-decision.md)).

The bare-repository refusal in Golem's own git calls (#803) is on by default
and covers only the git Golem runs; your own git needs the setting under
[Known issues](#known-issues).

## Other consumer-visible changes

- A file deleted while a native sandbox checks the workspace no longer refuses
  the command (#845). Before each sandboxed command, Golem walks the workspace
  for git metadata and files hard-linked outside it; a file that git pruned
  during that walk could refuse the command. Golem now restarts the walk when
  it detects a change, makes at most three passes, and asks you to retry if the
  workspace keeps changing. Two consecutive walks with the same missing link
  count still refuse the command as linked outside the workspace.
- The AgentFlow modes (`-plan`, `-goal`, `-agentflow-status`,
  `-agentflow-resume`) reject the four new sandbox flags, as they already
  rejected `-sandbox` and `-sandbox-network`.

## Known issues

New in this release:

- **A planted bare repository can still reach git you run**
  ([#803](https://github.com/kstruzzieri/go-llm/issues/803)). On both
  backends, a sandboxed command can create a bare repository in the workspace,
  or change the config or hooks of one already there, such as a fixture under
  `testdata/`. Host git run from that directory or below it can discover it,
  and its configuration can run programs outside the sandbox. Golem's own git
  refuses it (above); your own git, your editor's and your scripts' do not
  unless told to. With git 2.38 or later, run
  `git config --global safe.bareRepository explicit`, and have editors, IDEs
  and scripts pass `-c safe.bareRepository=explicit` on each host git call.
  The setting rejects ordinary bare repositories discovered implicitly; git
  still honors `--git-dir` and `GIT_DIR`, and can exempt paths it recognizes as
  `.git`, linked-worktree or submodule metadata. A Seatbelt rule against new
  `HEAD` entries was measured and not shipped: it broke ordinary toolchains and
  fixtures, and left existing bare repositories writable. Detection after each
  command would fit best with #802's work; it is not committed.
  See [What each backend enforces](../golem.md#what-each-backend-enforces).
- **Declared toolchain roots on Linux**
  ([#722](https://github.com/kstruzzieri/go-llm/issues/722)). Whether the
  current Bubblewrap roots run `go build`, `go test`, `python3` and `git` from
  common Linux install locations is not yet verified, and Bubblewrap refuses the
  declared-root flags. #722 stays open for that.
- **Host git calls keep some trust on purpose.** Parallel task mode still runs
  the repository's hooks, filters and lazy fetch. A sandboxed command can still
  reach them through an include target, a `core.hooksPath` or a linked hook
  that lies in the workspace, or a git directory outside `.git`. Version-manager
  shims that pick the real git from files in the workspace, and a program your
  config names by an absolute path inside the workspace, are trust inputs.

Moved to v0.10.0:

- **Bubblewrap does not refuse git metadata created during a run**
  ([#802](https://github.com/kstruzzieri/go-llm/issues/802)). Bubblewrap
  protects the metadata that exists when a command starts; it cannot refuse a
  new `commondir`, `config.worktree`, or `hooks` or `info` where they are
  absent. Because git honors `commondir`, which redirects local config, the
  snapshot's assumption that local config is read-only does not hold on
  Bubblewrap until #802. #802 also carries #803's Bubblewrap leg. It targets
  the [v0.10.0 milestone](https://github.com/kstruzzieri/go-llm/milestone/7).

Pre-existing, found during this release:

- **A fallback model the provider no longer serves cuts the input ceiling to
  8192 tokens** ([#856](https://github.com/kstruzzieri/go-llm/issues/856)).
  Golem budgets each turn against the smallest context window in the agent
  chain, and counts a chain entry it cannot look up as 8192 tokens, so one
  missing fallback caps the whole session. Startup then reports
  `model context metadata unavailable`, which points at the wrong model.
  Repoint or remove the missing fallbacks in `models.json`. The fix is a
  Should item for this release and has not merged.
