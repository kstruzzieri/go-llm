## What was evaluated

`-strict-approval` suspends reusable approvals once a conversation is exposed to outside content or its origin is unknown. The evaluation measures what that costs in prompts and whether the work still completes, with strict approval off and on, over synthetic content only. Reach and behaviour are defined in the [strict approval section of docs/golem.md](../golem.md#strict-approval--strict-approval), and this record does not widen them.

## Scripted evaluation

[strict-mode-evaluation.md](strict-mode-evaluation.md) is generated by `TestStrictModeEvaluation`. A scripted model and a counting approver drive Golem's real REPL turns through eight workflows (clean loop, MCP read, accepted `/consult` advice, a native-sandbox row measured below, the headless stub-tool row, and legacy, clean and exposed resume).

The scripted `/consult` rows (row 3 and the native leg below) run with interceptors switched on but without the `-interceptors` detector chain, as the existing consult tests do. They measure approval behaviour once advice is accepted, not advisory screening.

## Native sandbox leg

`TestStrictModeEvaluationNative` (`cmd/golem/strict_evaluation_native_test.go`) runs on a native backend with `-sandbox-network allowed`. The conversation is exposed either by accepted `/consult` advice or by resuming a foreign record. It asserts that the command's `sandbox:` line shows the narrowed network label, that a TCP connection from `bash` to a local listener fails with nothing received, and that a clean control conversation connects. It prints one line per sub-test with `-v` and skips on a host with no native backend, so its result names the machine it ran on.

## Local-model pass

One pass, not a sample. A local model served by llama.cpp drove each interactive workflow through the REPL with a scripted driver that approved every prompt. The tools were a loopback MCP server and a local `/consult` stub, with synthetic content throughout. The pass records whether each task completed next to the prompts it cost.

## What strict approval does not cover

These are the limits of the reach in the [exposure tables in docs/golem.md](../golem.md#what-exposes-a-conversation):

- Workspace files, command output (including `curl` output) and web input do not expose a conversation. A poisoned workspace file or a fetched page does not suspend approvals.
- A live CLI MCP session runs on the host and is never network-narrowed: a command approved after an MCP read prompts once and then has the host's full network.
- A background job that is already running keeps the network it started with.
- On bwrap, pathname Unix sockets inside the workspace stay reachable from a network-narrowed command.
- Recalled agent-memory records, and files an exposed conversation wrote, read as workspace content to a later clean conversation.
- Strict approval governs actions, not what reaches the model: once a conversation is exposed, its content still goes to the configured model provider, hosted or local, on every later turn.
